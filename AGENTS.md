# Kwartrack — Agent Guide

This is the canonical repository guide for every coding agent. Tool-specific
instruction files should reference this file instead of duplicating its
contents.

Kwartrack is a personal finance tracker on Supabase, deployed at
<https://kwartrack.com>. The earlier SpacetimeDB + Clerk implementation is
preserved at the `v1-final` tag.

## Start here

Before working on any task, read:

1. [`specs_v2.md`](specs_v2.md) — authoritative features, data model, and UX.
2. This file — engineering workflow and repository conventions.
3. [`.impeccable.md`](.impeccable.md) — canonical design context for UI work.

For contributor-facing setup and project background, see [`README.md`](README.md)
and [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Stack

- React, TypeScript, Vite, React Router, React Hook Form, and Recharts
- Supabase Auth, Postgres, Realtime, and Storage
- Tailwind CSS with DaisyUI
- Vitest and Testing Library
- Biome for formatting and linting; do not add ESLint or Prettier
- pnpm, with runtime and package-manager versions pinned in `package.json`

## Commands

```bash
pnpm bootstrap          # install, start local Supabase, generate .env.local
pnpm dev                # Vite development server
pnpm preview            # preview the production web build
pnpm test               # web Vitest suite
pnpm test:watch         # web tests in watch mode
pnpm run ci             # Biome check without autofix (`pnpm ci` is reserved)
pnpm check              # Biome check with autofix
pnpm build              # web type-check and production build
pnpm mcp:dev            # local MCP server in watch mode
pnpm mcp:test           # MCP tests
pnpm mcp:build          # MCP TypeScript build
pnpm mcp:worker:build   # Cloudflare Worker dry-run build
pnpm mcp:worker:dev     # local Cloudflare Worker development server
pnpm supabase:start     # start local Supabase (Docker required)
pnpm supabase:reset     # rebuild local DB and load synthetic demo data
pnpm supabase:status    # show local service URLs and credentials
pnpm supabase:stop      # stop the local stack
pnpm types:gen          # regenerate local Supabase TypeScript types
```

Run `pnpm run ci`, the relevant tests, and the relevant builds before handing
off a change. Use the local Supabase stack when integration coverage applies.

## Project structure

```text

apps/web/public/        Static web assets and Cloudflare Pages routing files
apps/mcp/               MCP server and Cloudflare Worker

```

## Local development and data safety

- Development uses the local Supabase stack at `http://127.0.0.1:54321`, never
  the hosted production project.
- `.env.local` is gitignored and generated by `pnpm bootstrap`.
- `pnpm supabase:reset` destroys only local data, reapplies migrations, and loads
  `supabase/seed.sql`.
- Never add production data, production connection strings, copied password
  hashes, or hosted credentials to fixtures, tests, documentation, or commits.
- Integration tests use `SUPABASE_SECRET_KEY` from the generated `.env.local` and
  skip when that local key is absent.

When changing the schema:

```bash
pnpm exec supabase migration new <name>
# edit the new migration
pnpm supabase:reset
pnpm types:gen
```

## Deployment constraints

`main` deploys automatically through `.github/workflows/ci.yml`. CI validates the
web app and MCP package, applies changed migrations, deploys the web bundle to
Cloudflare Pages, and deploys the MCP Worker when its paths change.

- Keep migrations additive. For unavoidable destructive changes, use a staged
  add-then-remove rollout coordinated with application code.
- Production `VITE_*` values are baked into the web build. Add each new value to
  the CI `validate` environment and configure a repository secret or variable
  when it is not a safe checked-in constant.
- Worker secrets persist in Cloudflare; manage them with `wrangler secret put`.
- Do not manually deploy routine changes that should flow through `main` and CI.

## TypeScript and code quality

- TypeScript is strict.
- Do not use explicit `any` or `@ts-ignore`; narrow `unknown` values properly.
- Prefer inference where the type is obvious.
- Follow existing component, hook, query, and test patterns before introducing a
  new abstraction.
- Keep generated artifacts and local environment files out of commits.

## UI conventions

- Follow the audience, tone, theme, and design principles in `.impeccable.md`.
- Use DaisyUI semantic tokens instead of hard-coded colors.
- Treat `corporate` light mode and `business` dark mode as equally supported.
- Prefer DaisyUI components (`btn`, `modal`, `card`, `badge`, `table`) before
  custom utility stacks.
- Test both themes and relevant viewport sizes for UI changes.
- Tailwind v4 configuration lives in `apps/web/vite.config.ts` and
  `apps/web/src/index.css`; do not add `tailwind.config.js`.

## Git conventions

Use Conventional Commits: `type(scope): description`.

Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `perf`.

Common scopes: `ui`, `auth`, `accounts`, `transactions`, `tags`, `recurring`,
`budget`, `debts`, `splits`, `settings`, `overview`, `db`, `ci`.

Examples:

```text
feat(budget): add per-tag allocation table
fix(accounts): clamp monthly recurring day-of-month
refactor(transactions): extract balance-delta helper
```

Preserve unrelated user changes and never stage or commit files outside the task.
